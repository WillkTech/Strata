# Strata Monitor — Exploration Report: JSON Configuration Manager over Port Switching

Date: 2026-10-24. Exploration and design only: nothing was launched, stopped, renamed, or
written during this investigation.

Scope note: everything below is from repository inspection (plus two read-only test runs). The
prior port-switching work is already committed (`5b875514`, `71fd78c2`, `a4ccbf2a`, `58e69b90`);
only `docs/v0.2.2PortSwitch.md` is untracked. `tests.terminal.test_switcher` (32 tests) and
`tests.terminal.test_monitor_bundle` (11 tests) pass on the current tree.

Guiding principle: make configuration files the source of truth for future launches, not a
mechanism for mutating running servers.

## A. Findings on the existing port-switching implementation

What the flow does today (verified in code):

- `MonitorApp` lives in `strata_cli/monitor.py`. Keys `m`/`s` open
  `switcher.ModelSwitchScreen` (`strata_cli/switcher.py:449`). The dialog can: pick a model,
  stop the server, or change the port.
- A port choice returns `port:<n>` or `port:<n>:yes` to `MonitorApp._perform_port_change`
  (`monitor.py:561`). Two modes:
  - **Non-writable monitor** (no preset name, or `--url`/`--connection`): repoint the monitor's
    endpoint only. The server is explicitly *not* moved. This is by design and tested
    (`test_a_monitor_started_with_a_url_only_repoints`).
  - **Writable monitor** (launched by `strata launch`, or standalone with a running launch):
    write the **preset** (`launch/store.py`), write the **model config JSON** on disk, write the
    **runtime profile** (`strata_control/profiles.py`), then stop the old server (`runtime.stop`
    or SIGTERM via `lsof`) and relaunch (`runtime.start` or `switcher.launch_model`), adopting
    the config's API key.

Confirmed fragility (source evidence, not hypothesis):

1. **No single source of truth for "which config is running."** `_active_config()`
   (`monitor.py:407-458`) is a five-stage heuristic chain: telemetry model id → name/id/label
   match → PID command-line `--config` scan (`switcher.get_server_config_path`, added in
   `58e69b90`) → port match → preset-name substring → "if exactly one config, guess it." The
   handoff doc's root causes (model-name-vs-id mismatch, missing preset ownership) were real,
   and the fix *added heuristics* rather than establishing one identity source. The complexity
   is structural, not incidental.
2. **The multi-store write is not atomic and swallows failures.** The config-file write is a
   direct `open(path, "w")` + `json.dump` wrapped in `except Exception: pass`
   (`monitor.py:594-605`); the profile write likewise (`609-616`). A failed config write silently
   continues into the stop/restart. This is the **only writer in the project that breaks the
   atomic-write discipline** — `setup.py write_config` (~5974, atomic + `.bak`),
   `launch/store.py _private_write` (mkstemp + `strata_control.atomic.replace` + 0600),
   `strata_control/profiles.py _atomic`, `apps/host native-control.mjs save()` (`.bak` + temp +
   rename), and `serve/runconfig.py` (`.bak`) all do temp+rename; the monitor path does not.
3. **Partial application is reachable.** The preset write aborts the flow on failure, but a
   failed config/profile write does not roll back the preset. Three stores (preset, run config,
   profile) can end up disagreeing, and the restart then proceeds from whichever state survived.
4. **Two forked restart mechanisms.** `runtime.start(profile)` (the packaged/host path with
   leases, attestation, one-token smoke) vs `switcher.launch_model` (raw `Popen` of
   `serve.server --config … --port …`). The switcher's direct `Popen` bypasses the
   profile/runtime machinery entirely — a server started by the switcher has no launch record and
   no `launch_info`, which is precisely why the monitor had to invent key adoption
   (`_adopt_launch_info`).
5. **POSIX-only process plumbing** (inferred from code, not run on Windows):
   `switcher.get_server_pid` shells out to `lsof` (`switcher.py:59-74`). On Windows `lsof` is
   absent, so `get_server_pid` returns `None`, `stop_server_on_port` returns `True` ("nothing to
   stop"), and the live-move flow would silently skip the stop. `strata_control/winproc.py`
   exists for the packaged path, but the thin bundle carries no `strata_control`.
6. **Documentation drift.** `docs/TERMINAL.md:238` states the interactive monitor "**It never
   starts or stops the server**" — and its key list doesn't even mention `m`. Meanwhile
   `TERMINAL.md:188` documents the `m` switcher modal, and the code stops and starts servers.
   The monitor's read-only contract was broken by commit `5b875514` ("Make the monitor the model
   switcher"); the docs were only half-updated.

Why the symptom "config changed but server stayed" appears: both branches are
correct-by-design once you know the mode — a `--url` monitor repoints only; a writable monitor
whose `_active_config()` returns `None` saves the preset and says "nothing was restarted." But
from the user's seat the dialog offers "Change port" uniformly, and the outcome depends on
invisible ownership state (`_can_write_port`, `_preset_name`, the heuristic chain). That is the
definition of fragile coupling.

**Strategic decision (recommended): remove interactive port switching from the monitor.** Keep
the monitor read-only per `TERMINAL.md:238`. Specifically:

- **Remove** the live write-and-restart path (`_perform_port_change`'s confirmed branch, and with
  it the multi-store coordination).
- **Keep** "repoint my endpoint" — it is view-only, safe, and genuinely useful (`m` dialog's
  non-writable behavior).
- **Keep** model switching *as launching* only if the team wants it (see roadmap); the stop/launch
  actions in `ModelSwitchScreen` are the same fragile coupling and should follow the port action
  out, leaving the dialog a pure "choose what to launch next" picker that hands off to the
  existing launcher.
- Tests to update: ~10 of the 32 in `test_switcher.py` pin the write-and-restart behavior
  (`TestMonitorPortChange`, `test_a_writable_monitor_writes_the_preset_and_restarts`,
  `test_port_change_updates_config_file_on_disk`, `test_monitor_app_port_and_bindings`).

## C. Configuration contract

The files the manager should own are the **run configs** — `strata-<model>.json` in the
installation folder (this checkout: `strata-m5-64k.json`, `strata-qwen-512k.json`,
`strata-swift-512k.json`). They are a **distinct concept** from launch presets
(`strata.launch/1`, `launch-presets/`), serving profiles (`source_config` + `overrides`,
`profiles/`), tuning presets (`presets/`), and connections (`connections/`) — each with its own
schema, directory, and lifecycle. The manager targets run configs; it must not silently mutate
the others.

**Schema (verified against real files + writers):** top-level `exe`, `args` (ordered list of
strings), `cwd`, `tokenizer`, `model_name`, `arch`, `host`, `port`, `api_key`, `log`,
`vision{exe,mmproj,model,gpu,max_tokens}`; plus `SETUP_KEYS` extras (`lib_dirs`, `backend`, `env`,
`gpu`, `gpus_asked`, `layer_split`, `draft_vocab`, `args_written`) and server-read keys
(`sampling`, `mcp_servers`, `cors_origins`, `trusted_origins`, `allowed_hosts`, `before_load`,
`open_browser`, `mtp`, `lazy_load`, `idle_unload_s`, …) — the host's `KNOWN_KEYS` is the fullest
published union. The task brief's field list is **not exhaustive**; unknown keys must survive
round-trips (`serve/runconfig.py` docstring and `setup.py carry_over` both commit to this).

**Validity rules already in the project** (reuse, don't invent):

- `setup.py model_config()`: a JSON object with `exe` and `args`.
- `strata_control/models.py _read()`: regular file, not a symlink, < 1 MiB, valid JSON, non-empty
  `exe` and `tokenizer`, `args` all strings.
- `strata_control/profiles.py read_run_config()`: same core.
- `apps/host/run-config-check.mjs`: the error/warning split — invalid JSON or wrong-typed known
  keys = error; unknown key = warning with nearest name; "changes apply the next time the model
  starts." **This last sentence is the project's own documented contract: run-config edits are for
  the next start, never the live process.** The TUI manager should enforce exactly that.

**Identity:** the **filename** is the id. `setup.py model_id` = config name without path;
`switcher._describe_config` returns `id = basename`; the host regexes the filename;
`strata models inspect` takes "a setup config name without a path." `model_name` is
display/telemetry only — renaming a file changes the id; changing `model_name` changes what
telemetry reports (this is exactly the mismatch that broke port switching).

**Discovery:** two mechanisms exist. `switcher.discover_models()` (bundle-carried) scans
`os.getcwd()` + `REPO_ROOT` + `state_base()/launch`, skipping legacy 0.2.1 names — note it
**depends on the current working directory**. `strata_control/models.py all_installs()` (not
bundle-carried) resolves install folders explicitly (`--install-dir`/`STRATA_INSTALL_DIR` →
terminal's own folder → remembered installs → app install folder). The manager should reuse
`switcher.discover_models()` for the bundle path and `strata_control.models` where available, and
the shared file CRUD should resolve directories through `strata_control.paths`/`profiles` with
env overrides honored (`STRATA_PROFILE_DIR`, `STRATA_LAUNCH_PRESET_DIR`, …) — tests depend on
those overrides.

**How values flow to launch:** `strata launch` reads the run config, applies preset choices via
`derive_config` — **which overwrites `host`, `port`, `api_key` from the preset** — writes a
derived private copy to `state_base()/launch/<name>.json`, and syncs the shared profile's
overrides. So for a launch-preset run, the run config's `port` is *overridden by the preset's
port*. Editing the run-config port matters for setup.py-launched and host-launched instances;
for `strata launch` runs the preset wins. The manager UI should say this plainly when a config is
driven by a preset.

**Existing CRUD to reuse:** profiles have full CRUD + revisions + rollback + `$VISUAL/$EDITOR`
edit (`strata_control/profiles.py`). Run configs have read-only CLI
(`strata models list/inspect`) and a documented-keys web editor (`serve/runconfig.py`). **No
Python-side create/duplicate/rename/delete exists for run configs** — that is the genuine gap.
`strata config` currently only has `show` (connections), so a
`strata config list|show|edit|duplicate|rename|delete|validate` verb family has a natural home in
`monitor_commands.py`/`cli.py`.

## D. TUI integration options

**Hard constraint first (verified):** the thin monitor bundle (`packaging/monitor_bundle.py`,
schema 7) carries an explicit `SOURCES` list;
`test_bundle_carries_every_module_its_entry_point_imports` AST-walks the import closure and fails
if a new monitor-path module isn't listed — adding one bumps the schema to 8. The bundle carries
**no `strata_control` and no `strata_cli.launch`**, so manager code on the bundle path must be
**stdlib + Textual only** (with graceful fallbacks for `strata_control` imports, as
`connections.py` does). Size budget: the 96 KB test assertion, currently ~85 KB → **~11 KB
headroom**. A new screen module fits; a full structured-editor widget set might not.

**Ruled out / ranked:** Option A is wrong as the *management* home (it would mix
"choose what to launch" with file administration, and the dialog is a compact modal). Option C
alone is disproportionately expensive for the bundle. Option E alone fails the "mostly-TUI" brief.
**Recommend F: dedicated management screen (B) + external editor (D) first, structured editing
(C) as a later phase, all CRUD through one shared service (E).**

## E. Recommended interaction design

Keyboard-first, mirroring existing conventions (`Menu` cursor list, `ConfirmScreen` for
destructive actions, status line for feedback, `?` help):

1. **`o` opens the Configuration Manager** from any monitor view (base `MonitorApp` binding; `o`
   is free on both monitors — `c` collides with Connect-view copy). `m` remains the launch picker,
   minus live mutation.
2. **List:** discovered run configs, one row each: name (filename id), `model_name`, port, host,
   validation status (`ok` / `warn: …` / `error: …`), and a marker for "appears to be running"
   (best-effort, from the existing `_active_config` heuristics, labeled as such). Search reuses
   the monitor's `/` filter convention; sort by name.
3. **Summary pane** on selection: path, schema fields at a glance, args count, vision on/off,
   **api_key masked** (never printed whole — the Connect view's `k` toggle convention;
   `models.py` summaries already avoid secrets).
4. **Actions:** `n` new (from minimal template or duplicate-selected), `Enter` view/edit
   (structured form in the later phase; `$VISUAL`/`$EDITOR` now), `d` duplicate, `r` rename
   (filename; warns that `model_name` is separate), `x` delete (confirm; "only this file goes; the
   running server, model files, presets and profiles are untouched"), `l` launch this config →
   hands off to the existing launch flow (`strata launch --model-path`/preset machinery), never a
   direct `Popen` from the manager.
5. **Save is a file operation.** Validate before write (mirror `run-config-check.mjs` severity
   split: blocking = malformed JSON / missing `exe`/`args`/`tokenizer` / wrong-typed known keys;
   warnings = unknown keys, missing executables or model files — show, don't reject). Detect
   external modification between load and save (mtime+hash, like `profiles`'
   `expected_revision`); refuse silent overwrite of concurrent changes. Atomic replace + `.bak`,
   matching every other writer.
6. **Editing the active config:** banner "this config appears to be in use — changes apply to the
   next start," never a restart.

## F. Proposed architecture

- **New shared module `strata_cli/configstore.py`** (stdlib-only so the bundle can carry it):
  discovery (wrapping `switcher.discover_models()` paths + `strata_control.models.all_installs()`
  when importable), load/validate/save/create/duplicate/rename/delete, atomic write + `.bak`,
  external-change detection. This is the single CRUD service; the TUI screen and a future
  `strata config` CLI verb both call it. No competing CRUD in the screen.
- **New `strata_cli/config_screen.py`** (add to `SOURCES` → schema 8): the list+summary+actions
  screen, built on `tui.py` `Menu`/palettes and the `ConfirmScreen` pattern (which lives in
  `launch/screens.py`, *not* bundle-carried — so the screen needs a small local confirm modal or
  `ConfirmScreen` moves into `tui.py`; moving it is the cleaner, smaller change).
- **External editor:** stdlib `tempfile` + `subprocess` + `os.environ["VISUAL"/"EDITOR"]`, run via
  `asyncio.to_thread` (the monitor's existing pattern) or Textual `suspend_application`; validate
  the draft on return; keep the draft on failure (the `profiles.edit()` discipline).
- **Monitor stays read-only:** remove `_perform_port_change`'s write-and-restart branch and
  `_perform_switch_model`/`_perform_stop_server`'s process mutation (or gate them behind an
  explicit opt-in per `AGENTS.md` "a new feature is opt-in, and the default path stays
  byte-identical"); keep endpoint repointing. `ModelSwitchScreen` becomes "choose what to launch
  next" → existing launcher.
- **Boundary:** UI → `configstore` (files) → validation → *stop*. Launching stays with
  `strata launch` / `setup.py` / the host, each reading the same files.

## G. Safety and compatibility plan

- **File integrity:** temp+atomic-rename + `.bak` (project-wide convention; the monitor's current
  direct-write is the outlier and should adopt it). Preserve unknown fields — dict-level edits
  only; **do not** round-trip through `LaunchSettings.from_dict` (it drops unknown keys — correct
  for presets, wrong for run configs). Preserve `args` order.
- **Secrets:** `api_key` masked in every summary/log line; full value only in the file and
  (opt-in) the editor buffer.
- **Concurrency:** revision/mtime check before save (mirror `profiles.save(expected_revision=…)`);
  refuse on external change with a clear message.
- **Active config:** identification is best-effort (the `_active_config` chain is a heuristic; on
  Windows even the PID lookup is broken — POSIX-only `lsof`). Label it "appears to be in use,"
  never act on it.
- **Packaging:** new modules must be stdlib+Textual on the bundle path; `strata_control` imports
  need fallbacks (pattern: `connections.py`, `monitor_commands._file_words`). Schema bump to 8;
  keep the built `.pyz` under 96 KB (~11 KB headroom — the list screen should be lean; defer the
  structured editor until size is re-measured).
- **Do not change during this work:** setup.py/host 8080 vs CLI 8000 alignment (open owner
  decision — the manager treats `port` as per-file data and says nothing about defaults); the JSON
  schema itself; the web Settings view.

## H. Incremental implementation roadmap

1. **Phase 0 — decision + doc truth:** deprecate the live port-switch write path (remove or
   opt-in gate); fix `TERMINAL.md:238` drift; update the ~10 `test_switcher.py` tests that pin
   write-and-restart. Keep endpoint repointing.
2. **Phase 1 — `strata_cli/configstore.py`:** discovery + safe file CRUD + validation (mirroring
   `run-config-check.mjs` severities) + atomic writes; unit tests on temp dirs via the existing
   env-override hooks (`test_models.py`/`test_profiles.py` patterns). No UI.
3. **Phase 2 — Configuration Manager screen** in the monitor (list, summary, validation status,
   external-editor edit, duplicate, rename, delete, create, confirmations); `o` binding; schema 8;
   bundle-size re-measure.
4. **Phase 3 — structured editing** for the common fields (port, host, api_key, log, nested
   vision, ordered args list) with warnings-vs-errors feedback and unsaved-changes display — only
   if the bundle budget allows.
5. **Phase 4 — launch handoff:** "launch this configuration" from the manager invokes the existing
   launch flow; the manager itself never starts or stops anything.
6. **Deferred, separate:** the 8000-vs-8080 alignment decision for `setup.py`/`apps/host`/READMEs
   (the last open item from the old handoff — it is an owner decision, not a prerequisite).

## I. Open questions (cannot be answered by inspection)

1. **Bundle size after schema 8:** ~11 KB headroom is an estimate from the last recorded build
   (84,763 B). A new screen module plus a moved `ConfirmScreen` needs one measured build before
   committing to Phase 2's scope.
2. **Windows behavior of the current switcher** (the `lsof` finding is static analysis —
   unconfirmed on real hardware per `AGENTS.md`): does the live-move flow on Windows actually skip
   the stop silently? Only affects how loudly Phase 0 should deprecate, not the direction.
3. **Owner intent for `m`:** should the switcher modal survive as a pure launch-picker (my
   recommendation), or should model switching leave the monitor entirely, restoring the literal
   "read only" contract of `TERMINAL.md:238`?
4. **Rename semantics for setup-managed configs:** `setup.py write_setup_config` keys `carry_over`
   and `.bak` off the existing filename; is renaming a setup-written config officially supported,
   or should the manager warn "setup may not find this by its old name"? (Code suggests the
   filename is the id everywhere, but no test pins rename.)
5. **Whether `strata launch` runs should ever honor the run-config `port`** when a preset also
   sets one (today the preset wins via `derive_config`) — a product decision the manager's copy
   should state once decided.

---

**Bottom line:** the port-switching work is committed and green, but its root fix was a heuristic
matching chain over three stores with a non-atomic writer — fragile by construction, and it broke
the monitor's documented read-only contract. The durable direction is: make the JSON files the
source of truth (discovery → edit → validate → save), keep saving and launching as separate
operations, and let the existing launcher remain the only thing that touches processes. The
smallest useful first step is `configstore.py` + the manager screen with external-editor editing;
the structured editor follows once the bundle budget is measured.
